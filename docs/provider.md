Each request has a bounded response size and socket timeout. The clients use no credentials, redirects or retries.

## Prospective observation

Run this from the repository root on a Linux host with authorized access to the public Data API and CLOB. The example uses the wallet in the upstream SDK fixture. Replace it with the public trading wallet to observe.

```sh
python3 -m apps.server.observe 0x7c3db723f1d4d8cb9c550095203b686cb11e5c6b --seconds 10
```

The CLI fixes a 1–30 second UTC window beginning at the next whole second, then reads one page of new BUY activity. An optional `--index-wait N` delays that single read by 0–300 additional seconds to test late indexing without changing the window. The receipt counts returned rows and ordinary wallet-relative BUYs and reports whether more pages exist. If a BUY is visible, the CLI selects the earliest eligible event on the returned page and immediately requests that token's book. A paginated response remains incomplete even when this pair is usable for research. An empty response can reflect indexing lag. Maximum two GETs, 256 KiB per response, four-second socket timeout, and a command deadline 12 seconds beyond the selected window and indexing wait.

JSON output records event time, local retrieval times, transaction, condition and token IDs, exact reported price and shares, provider book timestamp, minimum size and price tick when supplied, and the best three displayed asks. A matched book includes its signed age at detection (detection minus source time in milliseconds), and the best ask less the leader price in price units per share. These descriptive measurements include no queue, fee or actual fill evidence. The source-to-receipt difference includes the chosen sampling window and possible clock skew. `observed` means the matching book was requested after detection and its source timestamp is between detection and receipt. The activity response must also cover the full window. A previously updated book can still be unchanged, but a pre-detection timestamp gives incomplete timing evidence. Clock inconsistencies, empty asks, unsupported responses and endpoint failures produce partial or unavailable evidence. Exit code 0 covers observed and waiting states, and 2 covers incomplete or unavailable evidence.

**Activity-only identity.** The ordinary public activity model exposes a transaction hash. A transaction can contain multiple fills and overlapping representations. The probe leaves `fillId` null and emits no copy signal, order, fee estimate or modeled return. Connecting these observations to a prospective shadow decision requires a reliable participant-relative fill identity, instrument version, and follower costs. The checked SDK distinguishes normal trades from combos and reports ask levels in descending price order. [Activity model](https://github.com/Polymarket/py-sdk/blob/81e8abfb2a131ef3874f8fe405c9d95b2123fcdf/src/polymarket/models/data/activity.py) · [Book model](https://github.com/Polymarket/py-sdk/blob/81e8abfb2a131ef3874f8fe405c9d95b2123fcdf/src/polymarket/models/clob/order_book.py) · [Book request](https://github.com/Polymarket/py-sdk/blob/81e8abfb2a131ef3874f8fe405c9d95b2123fcdf/src/polymarket/_internal/actions/clob.py)

On 2026-11-25 an initial one-second lookup was denied in cloud setup. After public connectivity was available, the same read completed and reported waiting. A separate direct token-matched CLOB read returned eight ask levels. This verifies response compatibility only.

For the prospective trial, we chose the most frequent BUY wallet in one public 100-trade page to increase the chance of observing activity. The selected wallet, `0xc69bd5567b40ef4d11922eaa57e1f9be1c642076`, accounted for ten BUY rows. The newest source timestamp in the selection page preceded retrieval by about 263 seconds. Each probe fixed its window before reading its trades. These samples share a wallet and market conditions.

- The first 30-second window exceeded the 20-row request budget and returned incomplete.
- In a four-second window the adapter observed a 5-share BUY at 0.002, then received the matching token/condition book 198 ms after detection. It showed a best ask of 0.002 for 113164.74 shares, a five-share minimum and 0.001 tick. The best displayed ask minus the leader price was 0.000 per share. The source timestamp preceded detection by 245 ms, so the receipt remains incomplete under the post-detection gate. The transaction reference is `0x2d01b38492b8ff2d672d784a6edacb7c3e5e96c1f9242e6a729d5959a3896614`.

- Another 30-second window included the four-second interval. Reading it after a deliberate 275-second indexing wait again exceeded the page budget. Increasing retrieval delay alone did not resolve the sampling limitation.

All three initial activity-window results were incomplete. One included a matched token book and none met the post-detection source-time gate. To test short-lived opportunities, the next experiment needs point-in-time book updates, stable participant-relative execution identity and applicable fees. No follower order, simulated return or live financial outcome was produced by these probes.

A fourth 30-second trial on the same wallet tested retaining evidence from a capped response. The first page returned 20 ordinary BUY rows and a continuation cursor. One five-share BUY at 0.002 matched a 71-level ask book with a 0.002 best ask. The book arrived 383 ms after detection, while its source timestamp preceded detection by 301 ms. The receipt preserved both the partial page coverage and the timing result. The transaction reference is `0xee3ee3bee0da17780a2a1727ac6e7103953f7df1174999b6a8abde0a032804a4`. None of the four windows established a post-detection executable price.

A follow-up read of `/v2/trades` for the same wallet, condition and event second (both maker and taker rows) returned two records on one complete page. Exactly one matched the target transaction, token, BUY side, price and size. Both Data API endpoints identify the transaction. Neither response supplied a log index or individual fill ID. ## Budgeted observations

The public trader screen samples a two-second window using the budget entered before the window opens. An HTTP request with an empty body keeps the original five-second window and immediate book read. From source, add `--budget 10` to the observation CLI for the budgeted protocol. An installed launcher also supports the finite `study` command in the README.

For the earliest ordinary BUY on the returned page, PolySia requests market terms and the Polygon receipt concurrently. The fixed public RPC batch contains only `eth_chainId` and `eth_getTransactionReceipt`. It verifies Polygon mainnet, the successful transaction, block and log consistency, the exchange address, the order owner's BUY side, the outcome token and both exact amounts. The taker's aggregate `OrderFilled` must agree with its adjacent `OrdersMatched`. Each match carries one log identity, the source order hash and block hash. Multiple eligible records for the same participant, outcome and transaction remain unresolved. Removed logs, rounded amount mismatches and unsupported contracts cannot establish an identity. This is a single-provider observation at retrieval time. Chain finality and later corrections remain unverified. [Exchange deployments](https://github.com/Polymarket/ctf-exchange-v2/blob/ccc0596074f4dfd62c944fbca4de252893b82b4b/README.md) · [Settlement events](https://github.com/Polymarket/ctf-exchange-v2/blob/ccc0596074f4dfd62c944fbca4de252893b82b4b/src/exchange/mixins/Events.sol) · [Public Polygon RPC](https://polygon-bor-rpc.publicnode.com/)

The book request starts two seconds after both checks finish. A capacity estimate requires a complete activity page, matching instrument flags, a book update from that evidence-check time through book receipt, and a receipt within five seconds of the checks and ten seconds of the source BUY. The source event has whole-second precision. Requests are bounded to three Polymarket GETs and one RPC batch per sampled BUY. Misses require only the activity GET. No retries or pagination occur inside a window.

The estimate walks the three lowest displayed asks up to 0.03 pUSD per share above the reported BUY. It rounds displayed size down to whole shares at each level and reserves the estimated taker fee rounded up to one micro-pUSD per level. The supported market terms specify a taker-only fee with exponent one. Each level uses shares × rate × price × (1 − price), with no rebates. The market and book must agree on tick and minimum size. A crossed book or an unsupported taker delay leaves capacity unknown. An explicitly empty bid side has no exit quote. The export retains the best bid, spread, gross ask cost, estimated fee and unspent budget when available. Displayed capacity uses an unfunded budget and carries no fill or performance claim. [CLOB market fields](https://docs.polymarket.com/api-reference/markets/get-clob-market-info) · [Protocol fees](https://docs.polymarket.com/trading/fees)

**Evidence on 2026-11-25.** The earlier fourth transaction matched the watched wallet's taker order at Polygon block 97946137, log 136. The counterparty order and settlement summary were additional representations of the same five-share trade. Three new five-second windows with research budgets of 1, 10 and 25 pUSD matched participant BUYs, but their books arrived 11,934, 11,767 and 10,555 ms after the reported BUY respectively. All three were skipped. Three one-second windows returned no BUY.

Two installed studies then used three two-second windows per wallet and 10 pUSD per window. The original wallet produced two capacity estimates and one miss. The second wallet, the most frequent BUY address on other conditions in a separate 100-trade selection page, produced three misses. Repeating the same six-window design with bid-side and instrument checks produced **one estimate and five misses**. In that sample, Polygon log 233 in block 97948494 matched a five-share taker BUY at 0.002. The book arrived 6,166 ms after the reported BUY. The best bid was 0.001 and the best ask 0.002. At that ask, 4,762 whole shares fit within 10 pUSD, including a 0.475248 pUSD estimated fee. The 0.001 spread was half the ask price. The five-share leader order recorded 490 micro-pUSD in fees. Applying the sampled base fee formula to its reported price and size gives 499 micro-pUSD. Account terms or venue rounding could matter. The cause of the nine-unit difference is unverified. All capacity estimates shared the same wallet and market.

A study saves its plan before sampling and flushes each attempt and receipt to a new JSON Lines file. An interrupted study lacks a completion summary. The summary includes waiting and failed windows and counts distinct matched logs and source orders. Gaps between windows are unobserved. Distinct orders do not establish statistical independence.
